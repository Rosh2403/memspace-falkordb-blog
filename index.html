Gemini creates embeddings; Clerk provides identity. Neither replaces the graph’s authorization or data model.

Memspace is a personal ontology for assistants that connect over MCP. The interesting part is not that it stores memories. It is that every durable artifact — source text, a structured claim, a frozen share into a space, a search vector, a pending extraction job—is a node or relationship in FalkorDB. Gemini only produces embeddings. Clerk only authenticates. The graph is the system of record.

Why one store. A separate vector database would introduce another synchronization boundary. Keeping the search indexes and authorization graph in FalkorDB lets retrieval recheck access against current membership before returning a hit—even when an index entry is stale.

Why a property graph, and why this one

Everyday personal memory is relational. A preference applies to a topic. A task depends on another task. A claim is supported by a source revision. A share exists only while a person is an active member of a space. Those are walks, not foreign keys you join after retrieval.

The team looked at Graphiti and Mem0 as design precedents for hybrid retrieval, then implemented an evidence-backed property graph with a versioned JSON/Zod contract. It is not RDF, OWL, or a reasoner. Schema 1.1 lives in src/ontology.ts. FalkorDB is the runtime: Redis-protocol graph with parameterized Cypher, unique constraints, native full-text, and native HNSW vectors, reached through the official falkordb Node client (^6.8.0).

Vectors never leave that graph. Gemini Embedding 2 (768 dimensions, cosine, normalized) writes vecf32 onto KnowledgeSearchDocument nodes. A provider failure leaves the source saved and reports pending indexing. Missing credentials fall back to keyword retrieval. The design does not require Pinecone, a separate Redis search cluster, or an OWL export.

Two named graphs, never one mixed bag

One FalkorDB server hosts two graphs, selected by name rather than by a second process. Clerk profile sync uses FALKORDB_GRAPH (sandbox_profiles in the sandbox, shared_memory locally). The application graph uses FALKORDB_MEMORY_GRAPH (sandbox_memory / shared_memory_app). User PII and memory content do not share labels.

Profiles graph

src/users.ts. User nodes keyed by Clerk ID. Unique constraint on clerkId. Delayed webhook updates cannot revive a tombstone: deletion nulls email and name and is terminal for that ID. Health check is RETURN 1 AS ok on a read-only query.

Application graph

src/memory.ts. Fifteen labels from Person through Publication, each with a range index and a unique id constraint. MemoryStore.init() waits until every constraint is OPERATIONAL. Tests create a unique synthetic graph name and delete it afterward. Hosted sandbox and production graphs are never the test target.

A memory is more than a row

A save is not an INSERT. remember MERGEs a Person, a Memory whose ID is a hash of owner plus idempotency key, a Revision, an OntologyJob, and ABOUT links to Entity nodes. Retrying the same key is a no-op. Changing the payload against a used key is a 409.

Authorization is a Cypher pattern, not a filter afterward

Membership is not permission to read everything in a space. Private memories stay private unless they are explicitly shared or published. Every read re-checks current edges. The access helper in MemoryStore is the whole policy for unstructured memories:

OPTIONAL MATCH (m)-[:SHARED_IN {active:true}]->(:Space)
  <-[membership:MEMBER_OF {active:true}]-(:Person {id:$user})
WITH m, count(membership) AS memberships
WHERE m.deletedAt IS NULL
  AND (m.owner=$user OR memberships>0)

Structured knowledge is stricter. A private claim must be owned by the caller, attached to an undeleted source at the current revision, and in active or disputed status. A shared hit walks the other way: Person -MEMBER_OF-> Space <-PUBLISHED_IN- Publication. Publishing copies a frozen projection — excerpt, attribution, entity type and name — and omits private aliases, source memory IDs, and supersession history. Retracting sets Publication.active=false. Retrying a retracted snapshot cannot republish it. Source edits do not mutate a share that already went out.

Graph expansion is permissioned the same way. Keyword recall seeds authorized memories, then walks ABOUT entities and SHARED_IN spaces — but the same access() clause is applied to every neighbor. One-hop knowledge expansion uses scoped entity IDs, not whole-graph search.

Hybrid retrieval without a second index product

recall_knowledge reports its own method: FalkorDB full-text plus Gemini vector search, reciprocal-rank fusion, and one-hop scoped entity expansion. Indexes are not global. Each authorized namespace gets its own full-text and vector index on a server-generated label KS_<hash(scope + embedding signature)>. User text never becomes Cypher. Incompatible embedding signatures cannot mix spaces.

StepWhat FalkorDB does
1. ScopePersonal user:… index, plus one space:… index per membership
2. Lexicaldb.idx.fulltext.queryNodes — TF-IDF-style, cap 201 per scope
3. Semanticdb.idx.vector.queryNodes — HNSW M=16, cosine distance ≤ 0.32, cap 200/100
4. GuardRe-MATCH INDEXES → claim or publication against current membership
5. FallbackIf ANN returns fewer than 20 live hits, exact vec.cosineDistance over the scope
6. FuseReciprocal-rank fusion, k=60, then bounded one-hop neighbor fetch

Two implementation details are more interesting than the parameter list. First, this pinned FalkorDB build returns cosine distance in a procedure column named score — lower is better — so the query aliases it and converts to similarity only after the cutoff. Second, newer FalkorDB images can reorder UNWIND + MERGE result rows when there is no ORDER BY. record_knowledge therefore returns claim IDs in input order rather than row order, so callers still map claimIds[i] to claims[i].

CALL db.idx.vector.queryNodes($label,'embedding',200,vecf32($vector))
YIELD node, score
MATCH (node)-[:INDEXES]->(c:KnowledgeClaim)-[:SUPPORTED_BY]->(m:Memory)
WHERE c.owner=$user
  AND c.sourceRevision=m.revision
  AND c.status IN ['active','disputed']
  AND m.deletedAt IS NULL
  AND score <= 0.32
RETURN c.payload AS payload, score AS distance
ORDER BY distance, c.id
LIMIT 100

A local ten-question regression compared hybrid claim retrieval with the older text-memory path: 10/10 expected sources in the top five hybrid seeds versus 3/10 for text search. That is a small end-to-end fixture check, not evidence of production accuracy. Graph tests separately prove scope isolation, revoked access, old revisions, retraction, idempotence, and forgetting against a real FalkorDB — using synthetic vectors so CI does not need a model key.

The job queue is also a graph

remember and revise_memory create an OntologyJob in the same write as the source revision. OpenRouter (or Gemini) never talks to FalkorDB. The model receives the source, the live domain schema, and a bounded set of that author's private current claims. It has no tools and no write path. Validated plans are stored on the job node so a crashed write retries the same batch input and stable key.

A worker checks every five seconds for pending jobs whose nextAt has passed, attempts are under five, and any lease has expired. Claiming a job is a Cypher compare-and-set: status pending, lease empty or stale, then set a 120-second lease and increment attempts. Restarts resume eligible work. Forgetting nulls the plan and marks the job forgotten.

That is why extraction can survive a Railway restart without Redis Streams, Postgres, or an outbox table. The cost is operational: exhausted jobs stay pending with retryScheduled:false for an operator to inspect inside the intended environment — never by printing the private plan.

Job lifecycle:

  1. pending → lease 120s
  2. structured / no_supported_claims
  3. backoff, cap 5 attempts
  4. forgotten with the source
  5. superseded if the revision moved

Writes that survive retries, reads that survive revocation

Almost every mutation is MERGE plus a uniqueness constraint plus a hashed retry key. Revisions are compare-and-swap on Memory.revision. Sharing MERGEs SHARED_IN with active:true. Revocation sets MEMBER_OF.active=false; old invitation links cannot turn it back on. Forgetting does not delete the node. It nulls text, evidence, and payloads, deactivates shares, DETACH DELETEs search documents, and removes orphan Entity records. Minimal IDs remain so a replay cannot resurrect content.

Reads use graph.roQuery. Writes use graph.query. Parameters are always passed as $params — there is no string-built Cypher from user input. The dashboard graph view is a bounded authorized walk (LIMIT 300), rendered with React Flow only after the Ontology tab is opened.

The API service interpolates the FalkorDB private domain and password from Railway service references. /health fails closed with 503 if either graph query fails. Sandbox and production keep separate volumes, passwords, and graph names (sandbox_profiles / sandbox_memory). A code rollback does not undo graph writes.

What this choice bought, and what it did not

FalkorDB let Memspace keep one permissioned universe: unstructured memories, typed claims, frozen publications, search documents, and background jobs. Hybrid retrieval stays close to the data, with a small fusion layer instead of a distributed query planner. Tests can spin a uniquely named graph and throw it away.

It did not buy OWL inference, multi-hop query planning, learned reranking, or a transactional outbox for embeddings. Per-scope indexes isolate neighbors at the cost of administrative overhead as spaces grow. The exact-vector fallback is linear in scope size. Similarity is a relevance signal, never a truth confidence. Claims remain attributed assertions; the database will not decide that two people named Alex are the same person.
